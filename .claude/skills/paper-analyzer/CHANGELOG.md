# 🚀 v4.0.3（2026-09-19）— 表格竖线转义纪律 + 完成线自查（`_工具/table_check.py`）

> 背景：用户指出 `SM-MOEA-分析报告` 的**创新点表格**疑似有问题，要求用 skill 核查。排查确认缺陷真实存在，但**不在表格内容、而在渲染**：**§2.2 创新点表在 docx 里丢列**——C1 行（md 侧 10 个单元格）丢掉「本质区别/创新类型/含金量/为什么重要」四列且正文被截断，C2 行（8 个）丢掉「含金量 ★★★★☆/为什么重要」两列。根因 = **markdown 管道表格 + 单元格内未转义的裸竖线**：md 按 `|` 切格 → 该行列数**多于表头** → 渲染器（GFM 与 pandoc/docx）**把超出表头的单元格直接丢弃** → 靠右列**静默消失**，**md 源看起来完整**。skill 原文未提该纪律，属**规则缺失**（非「有规不遵」），故升版本。
> 动工前快照：`存档/skills-前版本/paper-analyzer-v4.0.2-2026-09-19-表格转义纪律前/`（整份，`__pycache__` 未纳入）。

## 1. 纪律：单元格内竖线一律转义 `\|` ⭐⭐⭐⭐⭐
- 落点：`SKILL.md` §2.2 + 「重要提醒 · 质量控制」第 6 条（原 6–9 条顺延为 7–10）；`templates/report-v4.md` §2.2 表旁提示（**模板提示，落报告前删本行**）。
- 写法：绝对值/基数竖线 → `\|`（`\|P\|×\|F\|`、`ρ=\|SM(e,j)−SM(i,j)\|/SM(e,j)`、`O(\|P\|·\|F\|)`）。
- **数学环境内另有一坑（本轮实测）**：`$…\|…$` 里的 `\|` 被 pandoc 按 LaTeX 解成 `\Vert` → 渲染成 **∥（U+2225）**；而 `\vert` / `\lvert` 在 pandoc 的 **markdown 读入器**里会被吃掉（`\v` 当重音符 → `$1 \ldots \vert F \vert$` 出 `1 …ert Fert`）。**可行写法 = 把竖线移出数学环境**：`$1 \ldots$ \|F\|` → docx 中 `1 … |F|`。
- **不必修的**：docx 中的 **∣（U+2223）** 是 pandoc 对 `\mid` / `\big|` 的既有渲染（条件熵 `H(F_j∣C)`、`P_i∣P_j`、集合基数），非缺陷。

> 背景：维护者批准「同方法修一下」——把 §3 留档的另外两处（`SPESS-分析报告` 11 行 / 32 个竖线、`…SPESS…/资料/评测脚本/评测协议说明.md` 1 行 / 2 个）按同法修掉（各自先快照、重出 docx、逐表复核）。**修的过程中实测出纪律本身缺的两块**，故在 v4.0.3 内补，不另起版本。

- **① 竖线若在行内代码段内，`\|` 不会被解析**：反引号代码段按字面输出 → docx 里是**可见的 `\|x\|`**（库内 32 个竖线中 **30 个**原在代码段内；`&#124;` 亦无效，实体在代码段内同样按字面显示）。修法 = 含竖线的那处**去掉反引号改普通文本**（`b = \|x\|` → docx 得 `b = |x|`）。实证：SM-MOEA 报告的勘误注自身也曾把 `\|` 写进代码段。
- **② 普通文本里的「反斜杠+字母」会被 pandoc 当 LaTeX 控制词吃掉**（**实测**：`|y\x|` → `|y|`，`x` 整个消失；`C:\Program Files\MATLAB\R2018b` → `C:Files2018b`）。这条是修 ① 时**自己踩出来的真内容丢失**：SPESS §4.2 #1 行的 `a* = |y\x|` 去掉反引号后 `\x` 被吞。修法 = **双写** `\\x`。**另发现**同类的库内既有缺陷：SM-MOEA `复现/README.md` 环境就绪表里的 Windows 路径（已按同法加反引号 + 快照）。

- **修复结果**：三份文件（SM-MOEA 20、SPESS 32、评测协议 2）表行内转义竖线齐备、**无含竖线的代码段**；SPESS / SM-MOEA 两份 docx 重出后与**修复前快照**逐段比对 = **insert / replace，纯删除 0**（图片逐字节一致、日期集合一致、docx 内无 `\|`）；全库裸反斜杠 3 → **0**。

### 2. Rate Limit 实际应对优化 ⭐⭐⭐⭐⭐

**问题发现**：
- Skill 文档说"并发调用不要超过 2 个"

- 影响：搜索失败，需要多次等待和重试

**解决方案**：
```javascript
// ✅ 新增：两种执行策略
// 策略 A（推荐）：完全串行执行
await search1()
await search2() // 严格等待

// 策略 B（激进）：最多 2 个并行 + 错误处理
try {
  const [r1, r2] = await Promise.all([search1(), search2()])
} catch (error) {
  if (error.code === 'RATE_LIMIT') {
    await sleep(60000) // 等待 60s
    retry()
  }
}
```

**新增内容**：
- 明确推荐串行执行（策略 A）

## 💡 关键经验总结

### 1. MCP 工具使用经验

**经验**：
- MCP 返回数据格式可能变化，**不要假设字段一定存在**
- Rate limit 比文档说的更严格（~1 rps 是真实限制）
- **必须准备 fallback 策略**

**最佳实践**：
- 先检查 MCP 可用工具列表（调用前验证）
- 使用串行执行（安全优先）
- 数据预处理（清洗、补字段）

---

### 2. 关键词搜索经验

**经验**：
- 泛化关键词（如 "speaker extraction"）返回大量噪音
- **精确组合关键词**效果最佳（方法论+架构+性能+应用）

**最佳实践**：
- 从 PDF 内容提取核心关键词（不要凭空想象）
- 使用四维组合策略
- 多轮搜索（先泛化，后精确）

---

### 3. 相似度判断经验

**经验**：
- "方法论相似"不是"同一领域"
- **必须明确判断依据**（标题关键词匹配、作者团队、架构名称）

**最佳实践**：
- 使用相似度评分模板（★★★★★）
- 区分演进/竞争/补充关系
- 避免选择直接竞争论文（性能碾压原文）

---

### 4. 并行执行经验

**经验**：
- Skill 说"可并行"，但 MCP rate limit 限制严重
- **实际串行执行更安全**

**最佳实践**：
- 步骤 2/3/4 可同时思考（Claude 内部并行）
- 步骤 5 搜索必须串行（外部工具限制）
- 使用 TaskCreate 跟踪进度（避免混乱）

# 🚀 v3.0（2026-08-05）— 提取/溯源/检索/表达 四项升级

## 1. 论文内容提取：修正 pdftoppm 误用 + 分层提取 ⭐⭐⭐⭐⭐

**问题发现**：v2 把 `pdftoppm`（poppler 的 **PDF→位图渲染器**，本身不产出文字）列为提取第一优先级，属误用；对带文字层的 PDF 反而丢文本。
**解决**：
- 明确工具职责：`pdftotext`(文字) / PyMuPDF/pdfplumber(文字+坐标) / pdftoppm(仅转图) / Read(视觉)。
- 新增 `scripts/pa_extract.py`：PyMuPDF 抽全文 + **逐页体检**（字符数/图片数/密度），自动标出"疑似图/扫描/稀疏页"→ 再走 Read 视觉或 OCR；`--layout` 复用 pdftotext 保版式。
- 实测：学位论文 94 页体检出 4 个需视觉页（含全页图 p.4）——判定正确。
- 手册：`references/extraction-strategy.md`（含 OCR 可选安装：RapidOCR/Paddle/Tesseract）。

## 2. 代码与数据集实体化溯源 ⭐⭐⭐⭐⭐
